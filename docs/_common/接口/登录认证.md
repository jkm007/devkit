# 登录认证接口文档

本文档按当前 `backend-server` 真实实现整理，覆盖账号密码登录、邮箱/短信验证码登录、注册、重置密码、Token 刷新、登出和当前用户认证接口。

## 接口概览

> 后端统一 API 前缀为 `/api/v1`。下表路径均省略此前缀。

| 接口 | 方法 | 用途 | 认证 |
|------|------|------|------|
| `/auth/captcha` | GET | 获取图形验证码 | 不需要 |
| `/auth/login` | POST | 用户名密码登录 | 不需要 |
| `/auth/login-by-email` | POST | 邮箱验证码登录 | 不需要 |
| `/auth/login-by-phone` | POST | 手机号短信验证码登录 | 不需要 |
| `/auth/send-code` | POST | 发送邮箱验证码 | 不需要，需先通过图形验证码 |
| `/auth/verify-code` | POST | 验证邮箱验证码 | 不需要 |
| `/auth/send-sms-code` | POST | 发送短信验证码 | 不需要，需先通过图形验证码 |
| `/auth/register` | POST | 用户注册 | 不需要，需邮箱验证码 |
| `/auth/reset-password` | POST | 重置密码 | 不需要，需邮箱验证码 |
| `/auth/refresh` | POST | 刷新 AccessToken 与 RefreshToken | 不需要，通过 Cookie、`X-Refresh-Token` 或请求体 `refreshToken` 校验 |
| `/auth/logout` | POST | 用户登出 | 可带 AccessToken；未带时仅清 Cookie |
| `/auth/codes` | GET | 获取当前用户权限码 | 需要 `Authorization: Bearer <accessToken>` |
| `/auth/permission-version` | GET | 获取权限版本 hash | 需要 |
| `/auth/change-password` | PUT | 修改当前用户密码 | 需要，需图形验证码 |
| `/user/info` | GET | 获取当前用户信息 | 需要 |
| `/user/info` | PUT | 更新当前用户资料 | 需要 |

## 1. 用户名密码登录

### 接口信息

- **路径：** `POST /auth/login`
- **用途：** 用户名密码登录，返回用户信息、AccessToken、RefreshToken，并写入安全 Cookie。
- **认证：** 不需要。
- **实现入口：** `internal/handler/auth_handler.go` 的 `Login`，业务逻辑在 `internal/service/auth_service.go` 的 `Login`。

### 请求体

```json
{
  "username": "vben",
  "password": "123456",
  "captchaId": "e7f0...",
  "captchaCode": "{\"x\":123,\"y\":45}",
  "captchaType": "slider",
  "startTime": 1717392000000,
  "points": []
}
```

### 请求字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `username` | string | 是 | 用户名，对应 `sys_users.name` |
| `password` | string | 是 | 明文密码，后端用 bcrypt 与 `sys_users.password` 比对 |
| `captchaId` | string | 条件必填 | 图形验证码 ID。验证码启用且达到触发条件时必填 |
| `captchaCode` | string | 条件必填 | 图形验证码答案。滑块/拼图/旋转为 JSON 字符串，数字为数字字符串，点选可配合 `points` |
| `captchaType` | string | 否 | 前端标识验证码类型，当前后端校验以 Redis 中保存的验证码类型为准 |
| `startTime` | number | 否 | 前端提交时的时间戳（毫秒），用于最短操作时间校验 |
| `points` | array | 否 | 点选验证码点击坐标数组 |

### 成功响应

```json
{
  "code": 0,
  "data": {
    "id": 1,
    "username": "vben",
    "nickname": "Vben",
    "realName": "vben",
    "email": "vben@example.com",
    "phone": "13800138000",
    "avatar": "",
    "gender": 0,
    "birthday": "1995-06-15",
    "bio": "",
    "roles": ["super"],
    "registerSource": "web",
    "homePath": "/analytics",
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "refreshToken": "eyJhbGciOiJIUzI1NiIs...",
    "mustChangePassword": false
  },
  "error": null,
  "message": "ok"
}
```

登录成功时后端同时写入：

```http
Set-Cookie: access_token=<accessToken>; Path=/; Max-Age=<access_token_ttl>; HttpOnly; Secure; SameSite=Lax
Set-Cookie: refresh_token=<refreshToken>; Path=/; Max-Age=<refresh_token_ttl>; HttpOnly; Secure; SameSite=Lax
```

### 失败响应

```json
// 参数错误
{
  "code": -1,
  "data": null,
  "error": "Username and password are required",
  "message": "Username and password are required"
}
```

```json
// 用户名或密码错误：后端对外统一返回通用错误，避免泄露账号是否存在
{
  "code": -1,
  "data": null,
  "error": "用户名或密码错误",
  "message": "用户名或密码错误"
}
```

```json
// 需要验证码或验证码错误，HTTP 200，业务码 403001
{
  "code": 403001,
  "data": null,
  "error": null,
  "message": "验证码错误，请重新验证"
}
```

### 后端校验流程

1. 读取 `sys_system_settings` 中 `group_key = 'captcha'` 的验证码配置，内存缓存 5 分钟。
2. 如果验证码关闭，直接进入账号密码校验。
3. 如果验证码开启：
   - `captcha_login_trigger = 0`：每次登录都要求验证码。
   - `captcha_login_trigger > 0`：检查 Redis 中 IP 和账号两个维度的失败计数：
     - `login_fail:ip:{clientIP}`
     - `login_fail:user:{username}`
     任一计数达到阈值则要求验证码。
4. 需要验证码时调用 `captcha.Verify(captchaId, captchaCode, startTime, points)`：
   - Redis `GETDEL captcha:{captchaId}` 获取并删除验证码，一次性使用，防重放。
   - AES-GCM 解密 Redis 中保存的答案。
   - 根据验证码类型做答案校验：数字、滑块、拼图、旋转、点选。
   - 校验最短操作时间，小于 `captcha_min_duration` 判定失败。
5. 根据 `username` 查询 `sys_users`。
6. 使用 `bcrypt.CompareHashAndPassword` 校验密码。
7. 检查 `sys_users.status`，只有 `1` 可登录。
8. 登录成功后清除 Redis 登录失败计数。
9. 收集角色：
   - 用户直接角色：`sys_user_roles` → `sys_roles`。
   - 分组继承角色：`sys_users.group_id` → `sys_group_roles`，递归父分组。
   - 如果没有角色，尝试自动分配默认 `user` 角色。
10. 生成 JWT AccessToken 和 RefreshToken。
11. 使用 SHA-256 哈希保存 RefreshToken 到 Redis：`refresh_token:{userID}`，TTL 30 天。
12. 更新 `sys_users.last_login_at`、`sys_users.last_login_ip`。
13. 记录安全日志到 `sys_security_logs`。
14. 记录或更新登录设备到 `sys_login_devices`。
15. 返回用户信息和 Token，并写入 `access_token`、`refresh_token` Cookie。

## 2. 邮箱验证码登录

### 接口信息

- **路径：** `POST /auth/login-by-email`
- **用途：** 使用邮箱和 6 位邮箱验证码登录。
- **认证：** 不需要。

### 请求体

```json
{
  "email": "user@example.com",
  "code": "123456"
}
```

### 后端校验流程

1. 调用 `VerifyCodeService.VerifyCode(email, code, "login")`。
2. 从 Redis 读取 `verify_code:login:{email}` 中保存的验证码 SHA-256 哈希。
3. 对提交的验证码做 SHA-256 后比较。
4. 失败时累加 `verify_code_fail:login:{email}`，达到 5 次锁定 15 分钟。
5. 成功后删除验证码 key 和失败计数 key。
6. 根据 `sys_users.email` 查询用户。
7. 检查用户状态 `status = 1`。
8. 复用 `generateLoginResponse` 生成 Token、记录登录信息。

### 失败保护

- Handler 对非验证码错误返回通用 `登录失败，请稍后重试`，避免泄露邮箱是否注册。
- 登录失败也会累加登录失败计数：`login_fail:ip:{ip}` 与 `login_fail:user:{email}`。

## 3. 手机号短信验证码登录

### 接口信息

- **路径：** `POST /auth/login-by-phone`
- **用途：** 使用手机号和 6 位短信验证码登录。
- **认证：** 不需要。

### 请求体

```json
{
  "phone": "13800138000",
  "code": "123456"
}
```

### 后端校验流程

1. 调用 `VerifyCodeService.VerifySMSCode(phone, code, "login")`。
2. 从 Redis 读取 `sms_code:login:{phone}` 中保存的验证码 SHA-256 哈希。
3. 校验失败累加 `sms_code_fail:login:{phone}`，达到 5 次锁定 15 分钟。
4. 校验成功后删除验证码 key 和失败计数 key。
5. 根据 `sys_users.phone` 查询用户。
6. 检查用户状态。
7. 复用 Token 生成和登录记录逻辑。

## 4. 发送邮箱验证码

### 接口信息

- **路径：** `POST /auth/send-code`
- **用途：** 发送注册、重置密码、邮箱登录验证码。
- **认证：** 不需要。
- **安全要求：** 发送前必须先通过图形验证码。

### 请求体

```json
{
  "email": "user@example.com",
  "purpose": "register",
  "captchaId": "e7f0...",
  "captchaCode": "1234",
  "startTime": 1717392000000
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `email` | string | 是 | 目标邮箱 |
| `purpose` | string | 是 | `register`、`reset_password`、`login` |
| `captchaId` | string | 是 | 图形验证码 ID |
| `captchaCode` | string | 是 | 图形验证码答案；点选验证码可传 JSON 数组字符串 |
| `startTime` | number | 否 | 前端提交时间戳 |

### 后端处理

1. Handler 先调用 `captcha.Verify` 校验图形验证码。
2. 检查邮箱验证码冷却 key：`verify_code_cooldown:{purpose}:{email}`，60 秒内不可重复发送。
3. 检查每日次数 key：`verify_code_daily:{purpose}:{email}`，同一邮箱同一用途每天最多 10 次。
4. 检查失败锁定 key：`verify_code_fail:{purpose}:{email}`，失败过多时拒绝发送。
5. 使用 `crypto/rand` 生成 6 位数字验证码。
6. 保存 SHA-256 哈希到 Redis：`verify_code:{purpose}:{email}`，TTL 5 分钟。
7. 通过邮件模板发送验证码。
8. 邮件发送失败时删除验证码 key 与冷却 key。

- **认证：** 不需要。

### 请求体

```json
{
  "phone": "13800138000",

  "captchaId": "e7f0...",
```

## 7. 用户注册

### 接口信息

- **路径：** `POST /auth/register`
- **用途：** 注册新账号。
- **认证：** 不需要。
- **前置条件：** 需要 `register` 用途邮箱验证码。

### 请求体

```json
{
  "username": "new_user",
  "email": "new@example.com",
  "emailCode": "123456",
  "password": "123456",
  "confirmPassword": "123456"
}
```

### 后端校验流程

1. 校验两次密码一致。
2. 校验用户名只包含字母、数字、下划线、连字符。
3. 校验邮箱验证码：`verify_code:register:{email}`。
4. 使用 bcrypt 加密密码。
5. 在数据库事务内：
   - 检查 `sys_users.name` 是否已存在。
   - 检查 `sys_users.email` 是否已存在。
   - 创建 `sys_users` 用户。
   - 查询 `sys_roles.name = 'user'`，存在则写入 `sys_user_roles` 分配默认角色。
6. 创建头像文件夹（失败不回滚）。
7. 记录 `sys_security_logs` 注册成功日志。

## 8. 重置密码

### 接口信息

- **路径：** `POST /auth/reset-password`
- **用途：** 通过邮箱验证码重置密码。
- **认证：** 不需要。

### 请求体

```json
{
  "email": "user@example.com",
  "emailCode": "123456",
  "newPassword": "654321",
  "confirmPassword": "654321"
}
```

### 后端校验流程

1. 校验两次密码一致。
2. 校验邮箱验证码：`verify_code:reset_password:{email}`。
3. 根据 `sys_users.email` 查询用户。
4. 检查 `sys_password_history` 最近 5 次密码，防止重复使用。
5. bcrypt 加密新密码并更新 `sys_users.password`、`password_changed_at`、`login_fail_count`。
6. 删除 Redis `refresh_token:{userID}`，使 RefreshToken 失效。
7. 删除权限缓存：`permission_codes:{userID}`。
8. 删除该用户所有登录设备记录。
9. 发送密码重置通知邮件（失败不阻断主流程）。
10. 记录 `sys_security_logs`。

## 9. 刷新 Token

### 接口信息

- **路径：** `POST /auth/refresh`
- **用途：** 使用 RefreshToken 轮换生成新的 AccessToken 和 RefreshToken。
- **认证：** 不需要 Authorization；优先读取 `refresh_token` Cookie，也兼容 H5/App 通过 `X-Refresh-Token` Header 或请求体 `refreshToken` 传递。

### 成功响应

```json
{
  "code": 0,
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "refreshToken": "eyJhbGciOiJIUzI1NiIs..."
  },
  "error": null,
  "message": "ok"
}
```

刷新成功后重新设置 `access_token` 和 `refresh_token` Cookie。

### 后端校验流程

1. 按优先级读取 RefreshToken：`refresh_token` Cookie → `X-Refresh-Token` Header → 请求体 `refreshToken`。
2. 使用 `jwt.Parse` 校验签名、算法和过期时间。
3. 根据 claims 中的 `userID` 查询用户与角色。
4. 生成新的 Token 对。
5. 计算旧 RefreshToken SHA-256 哈希与新 RefreshToken SHA-256 哈希。
6. 使用 Redis Lua 脚本原子执行：
   - 读取 `refresh_token:{userID}`。
   - 若不存在，返回过期或已登出。
   - 若旧哈希不匹配，判定为重放或并发刷新失败。
   - 匹配则 `SETEX` 新哈希，TTL 30 天。
7. 返回新 Token 并写 Cookie。

### 稳定性说明

刷新逻辑使用 Lua 脚本完成 read-verify-write，避免并发刷新时两个请求同时通过旧 RefreshToken 的 TOCTOU 竞态。并发情况下只有一个请求能成功，其他请求会因为哈希不匹配失败。

## 10. 用户登出

### 接口信息

- **路径：** `POST /auth/logout`
- **用途：** 清除当前登录状态。
- **认证：** 路由当前注册在公开 `/auth` 组，可带 Authorization 或 Cookie。

### 后端处理

1. 优先从 `Authorization: Bearer <token>` 读取 AccessToken；没有则读取 `access_token` Cookie。
2. 解析 AccessToken，计算 SHA-256 后写入 Redis 黑名单：`token_blacklist:{sha256(accessToken)}`，TTL 为 Token 剩余有效期。
3. 如果能确定 userID，则删除 `refresh_token:{userID}`。
4. 清空 `access_token` 与 `refresh_token` Cookie。

## 11. 修改密码

### 接口信息

- **路径：** `PUT /auth/change-password`
- **用途：** 当前登录用户修改自己的密码。
- **认证：** 需要 AccessToken。
- **安全要求：** 必须提交图形验证码。

### 请求体

```json
{
  "oldPassword": "123456",
  "newPassword": "654321",
  "confirmPassword": "654321",
  "captchaId": "e7f0...",
  "captchaCode": "1234"
}
```

### 后端校验流程

1. 校验图形验证码 `captcha.Verify`。
2. 校验两次新密码一致。
3. 校验密码长度：6 到 128 位。
4. 查询当前用户 `sys_users`。
5. bcrypt 校验旧密码。
6. 保存旧密码到 `sys_password_history`（失败只记录，不阻断）。
7. bcrypt 加密新密码并更新 `sys_users.password`、`password_changed_at`、`login_fail_count`、`must_change_password`。
8. 将当前 AccessToken 加入 Redis 黑名单：`token_blacklist:{sha256(accessToken)}`。
9. 删除 `refresh_token:{userID}`，强制重新登录。
10. 记录 `sys_security_logs`。

## 12. 获取权限码与权限版本

### 获取权限码

- **路径：** `GET /auth/codes`
- **认证：** 需要 AccessToken。
- **返回：** 当前用户所有权限码数组。

### 权限码来源

1. 用户直接角色：`sys_user_roles` → `sys_roles.permissions`。
2. 用户分组继承角色：`sys_users.group_id` → `sys_group_roles` → `sys_roles.permissions`。
3. `permissions` 字段为 JSON 数组，例如：

```json
["system:user:view", "system:user:add"]
```

权限码会缓存到 Redis：`permission_codes:{userID}`，TTL 10 分钟。

### 权限版本

- **路径：** `GET /auth/permission-version`
- **逻辑：** 获取权限码，排序后用 SHA-256 计算 hash，供前端轮询判断权限是否变化。

### 获取当前用户信息

- **路径：** `GET /user/info`
- **认证：** 需要 AccessToken。
- **返回：** 用户基础资料、角色、默认首页、是否强制改密等。

### 更新当前用户资料

- **可更新字段：** `nickname`、`email`、`phone`、`gender`、`birthday`、`bio`、`avatar`。
- **头像 URL 校验：** 允许 `/uploads/`、`/api/v1/files/`、`http://`、`https://`。

## 14. JWT 与 Cookie 机制

| Token | 存储位置 | 默认有效期 | 用途 |
|-------|----------|------------|------|
| AccessToken | 响应体 `data.accessToken`、HttpOnly Cookie `access_token` | 7 天 | 调用认证接口，通常放在 `Authorization: Bearer <token>` |
| RefreshToken | 响应体 `data.refreshToken`、HttpOnly Cookie `refresh_token` | 30 天 | 轮换刷新 Token |

JWT 使用 HS256 签名算法，解析时显式校验签名算法，避免 `alg=none` 类攻击。

## 15. H5 / 移动端接入说明

### 当前支持结论

当前登录认证接口是标准 HTTP JSON 接口，**接口层面已经支持 H5 调用**。H5 可以直接接入以下能力：

| 能力 | 当前是否支持 H5 | 说明 |
|------|----------------|------|
| 用户名密码登录 | 支持 | `POST /auth/login`，按需携带图形验证码 |
| 图形验证码 | 支持 | `GET /auth/captcha`，H5 自行渲染验证码 UI 并提交答案 |
| 邮箱验证码登录 | 支持 | `send-code` + `login-by-email` |
| 手机号验证码登录 | 支持 | `send-sms-code` + `login-by-phone`，推荐作为 H5 主要登录方式 |
| 注册 | 支持注册流程 | 注册请求支持 `registerSource`，允许 `web/h5/app/miniapp`，为空默认 `web` |
| 重置密码 | 支持 | 邮箱验证码重置密码 |
| Token 刷新 | 支持 | `/auth/refresh` 支持 Cookie、`X-Refresh-Token` Header、请求体 `refreshToken` 三种方式 |
| 登录设备记录 | 支持 | 登录时读取 `X-Client-Type`，允许 `web/h5/app/miniapp`，写入 `sys_login_devices.device_type` |

### H5 推荐登录流程

H5 端推荐优先使用手机号验证码登录：

```text
H5 打开登录页
  ↓
GET /api/v1/auth/captcha?type=slider
  ↓
用户完成图形验证码
  ↓
POST /api/v1/auth/send-sms-code
  ↓
用户输入短信验证码
  ↓
POST /api/v1/auth/login-by-phone
  ↓
保存 accessToken，后续请求使用 Authorization: Bearer <accessToken>
```

如果短信服务未配置，也可以使用邮箱验证码登录：

```text
GET /api/v1/auth/captcha?type=slider
  ↓
POST /api/v1/auth/send-code，purpose=login
  ↓
POST /api/v1/auth/login-by-email
```

### H5 Token 使用建议

当前后端登录成功会同时返回 Token 和写入 Cookie：

- 响应体：`accessToken`、`refreshToken`
- Cookie：`access_token`、`refresh_token`

H5 有两种接入方式：

#### 方式一：Cookie 模式

适合同域 H5 或已正确配置跨域凭证的 HTTPS H5。

要求：

1. H5 站点必须使用 HTTPS，因为登录 Cookie 设置了 `Secure`。
2. 后端 CORS 需要允许 H5 域名。
3. 前端请求需要开启 `withCredentials`。
4. `/auth/refresh` 可以自动读取 `refresh_token` Cookie。

#### 方式二：Authorization Token 模式

适合 App WebView、跨域 H5、非浏览器容器。

当前后端已经在登录响应体返回 `accessToken` 和 `refreshToken`，H5 可以保存 `accessToken`，后续请求使用：

```http
Authorization: Bearer <accessToken>
```

刷新 Token 时，`/auth/refresh` 已支持从 Header 或 Body 读取 RefreshToken：

```http
X-Refresh-Token: <refreshToken>
```

或：

```json
{
  "refreshToken": "<refreshToken>"
}
```

读取优先级为：

```text
Cookie refresh_token → Header X-Refresh-Token → Body refreshToken
```

### H5 CORS 配置

H5 独立域名部署时，需要把 H5 域名加入后端 CORS 白名单：

```yaml
cors:
  allow_origins:
    - "https://h5.example.com"
    - "https://m.example.com"
  allow_credentials: true
```

如果使用 Authorization Token 模式且不依赖 Cookie，也仍然需要允许：

```yaml
cors:
  allow_headers:
    - Authorization
    - Content-Type
    - X-Device-ID
    - X-Client-Type
    - X-Refresh-Token
    - X-App-Version
    - X-System-Version
    - X-Device-Model
    - X-Platform
    - X-Channel
    - X-Mobile-Token-Mode
    - X-Captcha-Id
    - X-Captcha-Code
    - X-Captcha-Start-Time
    - X-CSRF-Token
```

### H5 CSRF 注意事项

当前以下公开认证接口已经豁免 CSRF：

- `/auth/login`
- `/auth/login-by-email`
- `/auth/login-by-phone`
- `/auth/register`
- `/auth/reset-password`
- `/auth/send-code`
- `/auth/verify-code`
- `/auth/send-sms-code`
- `/auth/refresh`

认证后的 `POST` / `PUT` / `DELETE` 接口默认仍需要 CSRF。浏览器 H5 如果使用 Cookie 模式，需要从 `csrf_token` Cookie 读取并带上：

```http
X-CSRF-Token: <csrf_token>
```

如果 H5/App/小程序采用纯 Authorization Token 模式，并且不依赖 Cookie 认证，可以显式声明移动端 Token 模式跳过 CSRF：

```http
Authorization: Bearer <accessToken>
X-Client-Type: h5
X-Mobile-Token-Mode: true
```

后端会同时校验：

1. `X-Mobile-Token-Mode: true`。
2. `X-Client-Type` 是 `h5` / `app` / `miniapp`。
3. `Authorization` 是合法 Bearer Token。

只有同时满足以上条件才跳过 CSRF，Web Cookie 模式仍保留 CSRF 防护。

### 当前已实现的 H5 / App / 小程序正式用户端支持

当前代码已补齐正式用户端接入能力：

| 能力 | 当前实现 |
|------|----------|
| 注册来源 | `RegisterRequest` 支持 `registerSource`，允许 `web/h5/app/miniapp`，非法或为空默认 `web` |
| 设备类型 | 登录时读取 `X-Client-Type`，允许 `web/h5/app/miniapp`，写入 `sys_login_devices.device_type` |

| 设备类型筛选 | `GET /auth/devices?deviceType=h5` 支持按 `web/h5/app/miniapp` 筛选，前端设备管理页面已增加筛选 |
| RefreshToken 刷新 | `/auth/refresh` 支持 Cookie、`X-Refresh-Token` Header、请求体 `refreshToken` |

### 改动范围评估

如果现在要正式支持 H5，改动不算大，可以分三档推进：

#### 最小改动：只补文档和部署配置

- 不改代码。
- H5 使用现有接口。
- 部署时补 CORS H5 域名。
- H5 在 HTTPS + Cookie 正常的情况下使用现有 `/auth/refresh`。

适合：同域 H5 或普通浏览器 H5。

#### 已实现的推荐改动：补移动端标识和 Token 刷新兼容

当前已完成推荐改动：

1. 注册接口增加 `registerSource`，允许 `web/h5/miniapp/app`。
2. 登录记录设备时读取 `X-Client-Type`，支持 `h5`。
3. `/auth/refresh` 支持从 Header 或 Body 读取 RefreshToken。
4. CORS 允许 `X-Client-Type`、`X-Refresh-Token`。
5. 文档补充 H5 请求示例和接入说明。

适合：H5、App WebView、小程序 WebView 统一接入。

#### 已完成的正式用户端能力

在推荐改动基础上已继续完成：

1. 移动端 Token 存储策略规范。
2. 移动端设备 ID、设备名、系统版本、App 版本、平台、渠道上报。
3. 移动端登录设备管理按 `web/h5/app/miniapp` 筛选。
4. 针对移动端 Authorization 模式调整 CSRF 策略。

H5 独立前端项目或登录 SDK 不在当前仓库直接实现；当前仓库已提供统一接口、Header 规范、验证码接入方式和移动端 Token 策略，后续独立 H5 项目可直接按文档接入。

## 16. 统一响应格式

```json
{
  "code": 0,
  "data": {},
  "error": null,
  "message": "ok"
}
```

| HTTP Status | code | 说明 |
|-------------|------|------|
| 200 | 0 | 成功 |
| 200 | 403001 | 需要验证码或验证码错误，前端应弹出/刷新验证码 |
| 400 | -1 | 参数错误或业务校验失败 |
| 401 | -1 | 未授权，AccessToken 无效或已过期 |
| 403 | -1 | 禁止访问，RefreshToken 无效或账号密码错误 |
| 429 | -1 | 请求过于频繁 |
