# 验证码接口与后端实现文档

本文档按当前后端真实代码整理，重点说明图形验证码、邮箱验证码、短信验证码在登录与账号安全流程中的使用方式、后端校验方法、涉及配置、表和 Redis Key。

## 验证码分类

| 类型 | 后端类型值 | 用途 | 存储位置 | 校验入口 |
|------|------------|------|----------|----------|
| 图形验证码-数字 | `numeric` | 登录风控、发送邮箱/短信验证码前置校验、修改密码 | Redis `captcha:{captchaId}` | `pkg/captcha.Verify` |
| 图形验证码-滑块 | `slider` | 同上 | Redis `captcha:{captchaId}` | `pkg/captcha.Verify` |
| 图形验证码-拼图 | `puzzle` | 同上 | Redis `captcha:{captchaId}` | `pkg/captcha.Verify` |
| 图形验证码-旋转 | `rotation` | 同上 | Redis `captcha:{captchaId}` | `pkg/captcha.Verify` |
| 图形验证码-点选 | `point` | 同上 | Redis `captcha:{captchaId}` | `pkg/captcha.Verify` |
| 邮箱验证码 | 6 位数字 | 注册、重置密码、邮箱登录 | Redis `verify_code:*` | `VerifyCodeService.VerifyCode` |
| 短信验证码 | 6 位数字 | 手机号登录 | Redis `sms_code:*` | `VerifyCodeService.VerifySMSCode` |

## 1. 获取图形验证码

### 接口信息

- **路径：** `GET /api/v1/auth/captcha`
- **Query：** `type=numeric|slider|puzzle|rotation|point`
- **默认类型：** `numeric`
- **认证：** 不需要
- **实现入口：** `internal/handler/captcha_handler.go` 的 `GetCaptcha`

### 请求示例

```http
GET /api/v1/auth/captcha?type=slider
```

### 响应示例

```json
{
  "code": 0,
  "data": {
    "captcha_id": "e7f01b7a...",
    "image": "data:image/png;base64,...",
    "thumb": "data:image/png;base64,...",
    "thumb_y": 83,
    "type": "slider",
    "width": 320,
    "height": 200,
    "start_time": 1717392000000
  },
  "error": null,
  "message": "ok"
}
```

### 返回字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `captcha_id` | string | 验证码 ID，提交校验时作为 `captchaId` |
| `image` | string | 主图，通常为 base64 data URL |
| `thumb` | string | 滑块/拼图/旋转/点选的辅助图，数字验证码可为空 |
| `thumb_x` | number | 缩略图初始 X，当前主要保留扩展用途 |
| `thumb_y` | number | 滑块/拼图 Y 坐标提示 |
| `type` | string | 验证码类型 |
| `hint_text` | string | 点选验证码提示文案 |
| `chars` | string[] | 点选验证码字符列表 |
| `width` | number | 图片宽度 |
| `height` | number | 图片高度 |
| `length` | number | 数字验证码长度 |
| `start_time` | number | 后端生成时间戳（毫秒） |

### 限流

获取图形验证码接口按 IP 限流：

- Redis Key：`captcha_rate:{clientIP}`
- 窗口：1 分钟
- 阈值：每分钟最多 10 次
- 超限返回 HTTP 429：`验证码请求过于频繁，请稍后再试`

## 2. 图形验证码生成逻辑

图形验证码由 `pkg/captcha` 包实现，底层使用 `github.com/wenlng/go-captcha/v2` 生成图片。

### 生成流程

1. `captcha.Generate(captchaType)` 读取验证码配置：
   - 先使用内存缓存。
   - 缓存为空时从 `sys_system_settings` 查询 `group_key = 'captcha'` 的配置。
   - 查询失败时使用默认配置。
2. 根据 `captchaType` 调用对应生成函数：
   - `slider` → `generateGoSlide`
   - `puzzle` → `generateGoPuzzle`
   - `rotation` → `generateGoRotation`
   - `point` → `generateGoClick`
   - 其他或为空 → `generateGoNumeric`
3. 生成随机 `captchaId`。
4. 将答案序列化为 JSON 或字符串。
5. 使用配置中的验证码密钥做 AES-GCM 加密。
6. 保存到 Redis：`captcha:{captchaId}`。
7. 返回图片、验证码 ID、类型、尺寸和生成时间。

### Redis 保存结构

Redis 中保存的是 JSON 字符串，结构如下：

```json
{
  "type": "slider",
  "answer": "AES-GCM 加密后的答案",
  "start_time": 1717392000000
}
```

`answer` 不明文保存，避免 Redis 泄露时直接暴露验证码答案。

## 3. 图形验证码校验逻辑

### 统一校验方法

```go
captcha.Verify(captchaID, captchaCode, startTime, points)
```

| 参数 | 说明 |
|------|------|
| `captchaID` | 验证码 ID |
| `captchaCode` | 用户提交答案；数字为字符串，滑块/拼图/旋转为 JSON 字符串 |
| `startTime` | 前端提交时的时间戳（毫秒），用于最短操作时间判断 |
| `points` | 点选验证码点击坐标数组 |

### 校验步骤

1. 校验 `captchaID` 非空。
2. 读取当前验证码配置。
3. Redis `GETDEL captcha:{captchaID}` 获取并删除验证码。
   - 这意味着图形验证码一次性使用。
   - 成功、失败、格式错误都会消费该验证码。
4. 反序列化 Redis 中的 `CaptchaStore`。
5. 操作时间检查：
   - 如果提交了 `startTime` 且配置了 `captcha_min_duration`，计算 `startTime - store.StartTime`。
   - 小于最短操作时间则返回 `操作过于迅速，请重试`。
6. 根据 Redis 中保存的 `store.Type` 分发校验：
   - `slider`：解密答案，校验 X 坐标，使用滑块容差。
   - `puzzle`：解密答案，校验 X/Y 坐标，使用拼图容差。
   - `rotation`：解密答案，校验角度，使用旋转容差。
   - `point`：解密答案，按顺序校验点击坐标，使用点选容差。
   - 默认：数字验证码，忽略大小写比较字符串。

### 各类型提交格式

#### 数字验证码

```json
{
  "captchaId": "e7f0...",
  "captchaCode": "4829",
  "startTime": 1717392000800
}
```

#### 滑块验证码

后端只检查 X 坐标，Y 使用服务端答案值。

```json
{
  "captchaId": "e7f0...",
  "captchaCode": "{\"x\":185,\"y\":0}",
  "startTime": 1717392000800
}
```

#### 拼图验证码

后端同时检查 X 和 Y。

```json
{
  "captchaId": "e7f0...",
  "captchaCode": "{\"x\":185,\"y\":83}",
  "startTime": 1717392000800
}
```

#### 旋转验证码

```json
{
  "captchaId": "e7f0...",
  "captchaCode": "{\"angle\":126}",
  "startTime": 1717392000800
}
```

#### 点选验证码

点选验证码推荐通过 `points` 字段提交坐标。发送邮箱/短信验证码接口为了兼容，也支持将坐标 JSON 数组放到 `captchaCode` 中，Handler 会解析为 `points`。

```json
{
  "captchaId": "e7f0...",
  "captchaCode": "",
  "startTime": 1717392000800,
  "points": [
    { "x": 45, "y": 80 },
    { "x": 120, "y": 90 },
    { "x": 200, "y": 75 },
    { "x": 280, "y": 88 }
  ]
}
```

## 4. 登录验证码触发规则

用户名密码登录的验证码不是固定必填，而是由系统设置控制。

### 配置来源

`AuthService.getCaptchaSettings()` 从 `sys_system_settings` 读取：

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `captcha_enabled` | 是否启用登录验证码 | `true` |
| `captcha_login_trigger` | 登录失败几次后要求验证码，`0` 表示始终要求 | `3` |

该配置在认证服务中有 5 分钟内存缓存。

### 触发逻辑

1. `captcha_enabled = false`：不校验登录验证码。
2. `captcha_enabled = true` 且 `captcha_login_trigger = 0`：每次用户名密码登录都要求验证码。
3. `captcha_enabled = true` 且 `captcha_login_trigger > 0`：
   - 检查 Redis `login_fail:ip:{clientIP}`。
   - 检查 Redis `login_fail:user:{username}`。
   - 任一计数达到阈值后要求验证码。

### 登录失败计数

用户名不存在或密码错误时记录：

| Key | 说明 | TTL |
|-----|------|-----|
| `login_fail:ip:{clientIP}` | IP 维度失败计数 | 30 分钟 |
| `login_fail:user:{username}` | 账号维度失败计数 | 30 分钟 |

登录成功后删除这两个 key。

## 5. 邮箱验证码

### 发送接口

- **路径：** `POST /api/v1/auth/send-code`
- **用途：** 发送注册、重置密码、邮箱登录验证码。
- **前置校验：** 必须先通过图形验证码。

### 请求体

```json
{
  "email": "user@example.com",
  "purpose": "register",
  "captchaId": "e7f0...",
  "captchaCode": "1234",
  "startTime": 1717392000800
}
```

`purpose` 可选值：

| 值 | 说明 |
|----|------|
| `register` | 注册账号 |
| `reset_password` | 重置密码 |
| `login` | 邮箱验证码登录 |

### 后端发送流程

1. Handler 校验请求参数。
2. 如果 `captchaCode` 是 JSON 数组字符串，解析为点选验证码坐标。
3. 调用 `captcha.Verify` 校验图形验证码。
4. `VerifyCodeService.SendCode(email, purpose)` 执行发送逻辑：
   - 检查 60 秒冷却。
   - 检查每日发送上限 10 次。
   - 检查验证码失败锁定。
   - 使用 `crypto/rand` 生成 6 位数字验证码。
   - 使用 SHA-256 保存验证码哈希到 Redis。
   - 设置冷却 key 和每日计数 key。
   - 渲染邮件模板并发送 HTML 邮件。
5. 邮件发送失败时删除验证码 key 和冷却 key。

### Redis Key

| Key | 说明 | TTL |
|-----|------|-----|
| `verify_code:{purpose}:{email}` | 验证码 SHA-256 哈希 | 5 分钟 |
| `verify_code_cooldown:{purpose}:{email}` | 发送冷却 | 60 秒 |
| `verify_code_daily:{purpose}:{email}` | 每日发送计数 | 到当天结束 |
| `verify_code_fail:{purpose}:{email}` | 校验失败计数 | 15 分钟 |

### 校验接口

- **路径：** `POST /api/v1/auth/verify-code`

```json
{
  "email": "user@example.com",
  "code": "123456",
  "purpose": "register"
}
```

### 校验流程

1. 检查失败次数是否达到 5 次。
2. 读取 `verify_code:{purpose}:{email}`。
3. 对提交的验证码做 SHA-256 后与 Redis 哈希比较。
4. 失败：递增 `verify_code_fail:{purpose}:{email}`，TTL 15 分钟。
5. 成功：删除验证码 key 和失败计数 key。

## 6. 短信验证码

### 发送接口

- **路径：** `POST /api/v1/auth/send-sms-code`
- **用途：** 发送手机号登录验证码。
- **前置校验：** 必须先通过图形验证码。

### 请求体

```json
{
  "phone": "13800138000",
  "purpose": "login",
  "captchaId": "e7f0...",
  "captchaCode": "1234",
  "startTime": 1717392000800
}
```

### 后端发送流程

1. Handler 参数校验。
2. 校验图形验证码。
3. `VerifyCodeService.SendSMSCode(phone, purpose)` 执行发送逻辑：
   - 检查 60 秒冷却。
   - 检查每日发送上限 10 次。
   - 检查失败锁定。
   - 使用 `crypto/rand` 生成 6 位验证码。
   - SHA-256 哈希保存到 Redis。
   - 根据 SMS 配置选择阿里云或腾讯云发送器。
4. 短信发送失败时删除验证码 key 和冷却 key。

### Redis Key

| Key | 说明 | TTL |
|-----|------|-----|
| `sms_code:{purpose}:{phone}` | 短信验证码 SHA-256 哈希 | 5 分钟 |
| `sms_code_cooldown:{purpose}:{phone}` | 发送冷却 | 60 秒 |
| `sms_code_daily:{purpose}:{phone}` | 每日发送计数 | 到当天结束 |
| `sms_code_fail:{purpose}:{phone}` | 校验失败计数 | 15 分钟 |

## 8. 风险评分验证码

除认证接口自身的验证码逻辑外，认证后的接口还会经过 `CaptchaGuard` 风险评分中间件。

### 生效位置

`router.Setup` 中认证接口组使用：

```go
authorized.Use(middleware.JWTAuth())
authorized.Use(middleware.SecurityLogMiddleware())
authorized.Use(middleware.CaptchaGuard())
```

### 关键规则

1. 跳过 `/api/v1/auth/` 路径，因为认证相关接口有自己的验证码校验。
2. 只对风控配置中的受保护路径生效。
3. 根据 IP、路径、请求头、访问频率等规则计算风险分。
4. 风险分低于阈值直接放行。
5. 风险分达到阈值时，要求请求头携带：
   - `X-Captcha-Id`
   - `X-Captcha-Code`
   - `X-Captcha-Start-Time`
6. 未携带或验证码错误时，返回 HTTP 200 + `code = 403001`，并随机返回一种验证码类型。
7. 验证成功后写入白名单 `captcha:whitelist:{ip}`，10 分钟有效，并将风险分减半。

### 风险评分相关 Redis Key

| Key | 说明 |
|-----|------|
| `risk:score:{ip}` | IP 风险总分 |
| `risk:freq:{ip}` | 频率规则计数 |
| `risk:window:{ip}` | 滑动窗口请求记录 |
| `captcha:whitelist:{ip}` | 验证码通过白名单，10 分钟 |

## 9. 配置项

验证码配置存储在 `sys_system_settings` 表，`group_key = 'captcha'`。

| key | 默认值 | 说明 |
|-----|--------|------|
| `captcha_enabled` | `true` | 是否启用登录验证码 |
| `captcha_type` | `"slider"` | 前端默认展示验证码类型 |
| `captcha_expire` | `120` | 图形验证码有效期，单位秒 |
| `captcha_max_fail` | `5` | 最大失败次数配置，当前主要作为配置项保留 |
| `captcha_login_trigger` | `3` | 登录失败几次后要求验证码，`0` 表示始终要求 |
| `captcha_min_duration` | `500` | 最短操作时间，单位毫秒 |
| `numeric_length` | `4` | 数字验证码长度，未配置时使用默认值 |
| `numeric_width` | `160` | 数字验证码宽度 |
| `numeric_height` | `60` | 数字验证码高度 |
| `slider_width` | `320` | 滑块验证码宽度 |
| `slider_height` | `200` | 滑块验证码高度 |
| `slider_tolerance` | `5` | 滑块容差 |
| `puzzle_width` | `320` | 拼图宽度 |
| `puzzle_height` | `200` | 拼图高度 |
| `puzzle_tolerance` | `5` | 拼图容差 |
| `puzzle_vertical_random` | `true` | 拼图 Y 轴是否随机 |
| `rotation_size` | `220` | 旋转验证码图片尺寸 |
| `rotation_thumb_size` | `80` | 旋转缩略图尺寸 |
| `rotation_tolerance` | `10` | 旋转角度容差 |
| `point_width` | `320` | 点选验证码宽度 |
| `point_height` | `220` | 点选验证码高度 |
| `point_count` | `4` | 点选验证码目标字符数 |
| `point_tolerance` | `30` | 点选坐标容差 |

> `InitDefaultSettings()` 只在 captcha 分组没有任何配置时写入基础默认项；更多细分配置未在数据库配置时由代码默认值兜底。

### 配置缓存刷新

后台更新 `captcha` 分组配置后，`SystemSettingService.Update` / `UpdateByGroup` 会调用：

```go
captcha.RefreshConfig()
```

认证服务中的 `captcha_enabled`、`captcha_login_trigger` 还有独立 5 分钟内存缓存，可通过 `InvalidateCaptchaSettingsCache()` 主动失效。

## 10. 安全设计

| 设计 | 说明 |
|------|------|
| 一次性使用 | 图形验证码使用 Redis `GETDEL`，校验后立即删除 |
| 答案加密 | 图形验证码答案使用 AES-GCM 加密保存 |
| 传输不返回答案 | 接口只返回图片、ID、提示，不返回正确答案 |
| 最短操作时间 | 使用 `captcha_min_duration` 拦截过快操作 |
| 登录失败触发 | 通过 IP 与账号两个维度统计失败次数 |
| 邮箱/短信冷却 | 60 秒内禁止重复发送 |
| 每日次数限制 | 同一邮箱/手机号同一用途每天最多 10 次 |
| 验证失败锁定 | 邮箱/短信验证码连续失败 5 次锁定 15 分钟 |
| 哈希存储 | 邮箱/短信验证码只保存 SHA-256 哈希 |
| 图形验证码前置 | 发送邮箱/短信验证码前必须先过图形验证码 |
| 风险评分 | 高风险认证后接口会被 `CaptchaGuard` 要求验证码 |

## 11. H5 / 移动端验证码接入说明

### 当前支持结论

图形验证码接口是标准 HTTP 接口，**H5 可以直接使用**。后端不关心验证码由 PC 组件还是 H5 组件渲染，只校验最终提交的数据是否符合后端保存的答案。

H5 可直接调用：

```http
GET /api/v1/auth/captcha?type=slider
```

然后在登录、发送邮箱验证码、发送短信验证码或修改密码时提交：

```json
{
  "captchaId": "验证码ID",
  "captchaCode": "用户答案",
  "startTime": 1717392000800,
  "points": []
}
```

### H5 推荐验证码类型

| 类型 | H5 适配建议 | 说明 |
|------|-------------|------|
| `numeric` | 简单可用 | 适合低风险场景，H5 实现成本最低 |
| `slider` | 推荐 | 适合 H5 登录，交互简单 |
| `puzzle` | 可用 | 需要 H5 准确计算滑块 X/Y 坐标 |
| `rotation` | 可用 | 需要 H5 滑动或旋转交互组件 |
| `point` | 可用但成本较高 | 需要 H5 记录点击坐标顺序 |

如果 H5 初期快速接入，建议优先使用：

```text
slider 或 numeric
```

### H5 滑块验证码提交示例

获取验证码：

```http
GET /api/v1/auth/captcha?type=slider
```

后端返回：

```json
{
  "captcha_id": "e7f0...",
  "image": "data:image/png;base64,...",
  "thumb": "data:image/png;base64,...",
  "thumb_y": 83,
  "type": "slider",
  "width": 320,
  "height": 200,
  "start_time": 1717392000000
}
```

H5 用户拖动后，提交登录：

```json
{
  "username": "demo",
  "password": "123456",
  "captchaId": "e7f0...",
  "captchaType": "slider",
  "captchaCode": "{\"x\":185,\"y\":0}",
  "startTime": 1717392000800
}
```

滑块验证码后端只校验 X 坐标，Y 使用服务端保存的答案值。

### H5 点选验证码提交示例

点选验证码需要按顺序提交坐标：

```json
{
  "captchaId": "e7f0...",
  "captchaType": "point",
  "captchaCode": "",
  "startTime": 1717392000800,
  "points": [
    { "x": 45, "y": 80 },
    { "x": 120, "y": 90 },
    { "x": 200, "y": 75 },
    { "x": 280, "y": 88 }
  ]
}
```

发送邮箱/短信验证码接口也兼容把点选坐标 JSON 数组放在 `captchaCode` 中，但为了清晰，H5 新实现建议直接使用 `points` 字段的模式。

### H5 接入注意事项

1. 图形验证码一次性使用，失败后必须重新获取。
2. H5 需要使用后端返回的 `start_time` 计算并提交操作完成时间戳，避免触发“操作过于迅速”。
3. 发送邮箱/短信验证码前必须先完成图形验证码。
4. H5 跨域部署时，后端 CORS 需要允许 H5 域名。
5. 如果 H5 使用 Cookie 模式，必须启用 HTTPS 和 `withCredentials`。
6. 如果 H5 使用纯 Token 模式，验证码接口本身不受影响；当前 Token 刷新已支持 Header/Body RefreshToken 模式。

### 支持 H5 的改动评估

验证码部分支持 H5 的改动较小：

- 后端验证码生成和校验逻辑无需重写。
- H5 端只需要实现验证码 UI，把答案转换成后端需要的格式。
- 当前后端已补充 Header 白名单和移动端 Token 刷新兼容。

如果只做 H5 登录页面，优先实现 `slider` / `numeric` 两种验证码即可。

## 12. 涉及数据表

| 表名 | 用途 |
|------|------|
| `sys_system_settings` | 保存验证码类型、启用状态、有效期、容差、登录触发阈值等配置 |
| `sys_users` | 登录时读取用户账号、密码、状态、邮箱、手机号等 |
| `sys_security_logs` | 记录登录失败、登录成功、注册、改密、重置密码等安全事件 |
| `sys_login_devices` | 登录成功后记录设备 |
| `sys_password_history` | 重置密码/修改密码时检查或记录历史密码 |

图形验证码、邮箱验证码、短信验证码本身不落 MySQL 表，均使用 Redis 临时保存。
