# 登录与验证码后端校验流程

本文档补充说明登录和验证码的完整稳定流程：后端如何判断是否需要验证码、如何校验验证码、如何校验账号密码、如何生成和刷新 Token，以及整个过程用到了哪些方法、数据表和 Redis Key。

## 1. 总体流程

```text
前端
  │
  │ 1. 读取公开系统配置 /system/settings/public，决定默认验证码类型等展示信息
  │
  ├─ 2. 获取图形验证码 GET /auth/captcha?type=slider
  │       后端生成图片 + captchaId，答案 AES-GCM 加密写入 Redis captcha:{captchaId}
  │
  ├─ 3. 提交登录 POST /auth/login
  │       username/password/captchaId/captchaCode/startTime/points
  │
后端 AuthHandler.Login
  │
  ├─ 4. AuthService.checkCaptcha
  │       读取验证码配置，结合登录失败计数判断是否必须校验图形验证码
  │
  ├─ 5. captcha.Verify
  │       Redis GETDEL 一次性取出 captcha:{captchaId}
  │       解密答案并按类型校验
  │
  ├─ 6. 查询 sys_users
  │       校验用户存在、bcrypt 密码、账号状态
  │
  ├─ 7. 收集角色和权限上下文
  │       sys_user_roles / sys_roles / sys_groups / sys_group_roles
  │
  ├─ 8. jwt.Generate
  │       生成 AccessToken 和 RefreshToken
  │
  ├─ 9. 保存 RefreshToken 哈希
  │       Redis refresh_token:{userID} = sha256(refreshToken)，TTL 30 天
  │
  ├─ 10. 更新登录信息和审计记录
  │       sys_users / sys_login_devices / sys_security_logs
  │
  └─ 11. 返回响应并写 Cookie
          access_token + refresh_token，HttpOnly + Secure + SameSite=Lax
```

## 3. 用户名密码登录稳定流程

### 3.1 判断是否需要验证码

后端先执行 `AuthService.checkCaptcha`：

1. 调用 `getCaptchaSettings()` 读取验证码设置。
2. 读取来源：`sys_system_settings`，条件为 `group_key = 'captcha'`。
3. 只关心两个核心配置：
   - `captcha_enabled`
   - `captcha_login_trigger`
4. 配置有 5 分钟内存缓存，减少每次登录查库。
5. 判断逻辑：
   - 未启用验证码：直接放行到账号密码校验。
   - `captcha_login_trigger = 0`：始终要求图形验证码。
   - `captcha_login_trigger > 0`：检查 Redis 失败计数。

失败计数 Key：

```text
login_fail:ip:{clientIP}
login_fail:user:{username}
```

任一计数达到阈值，就必须提供图形验证码。

### 3.2 校验图形验证码

如果需要验证码但请求没有 `captchaId`，返回错误：

```text
Please complete the captcha
```

Handler 会将包含“验证码 / captcha / 验证失败”的错误转换为：

```json
{
  "code": 403001,
  "data": null,
  "error": null,
  "message": "验证码错误，请重新验证"
}
```

实际验证码校验由 `captcha.Verify` 完成：

1. Redis `GETDEL captcha:{captchaId}`。
2. 解析保存的验证码类型和加密答案。
3. 如果配置了最短操作时间，判断提交时间是否过快。
4. AES-GCM 解密答案。
5. 根据类型校验用户答案。

`GETDEL` 是稳定性的关键：验证码无论成功失败都会被消费，避免重复提交和重放。

### 3.3 校验账号密码

验证码通过后，`AuthService.Login` 执行账号密码校验：

1. `userRepo.GetByName(req.Username)` 查询 `sys_users.name`。
2. 用户不存在：记录登录失败计数，返回统一错误。
3. 使用 bcrypt 校验：

```go
bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(req.Password))
```

4. 密码错误：记录登录失败计数，返回统一错误。
5. 检查 `sys_users.status`，只有 `1` 允许登录。
6. 登录成功：删除 IP 与账号两个维度失败计数。

### 3.4 生成 Token 与登录态

账号校验通过后调用 `generateLoginResponse`：

1. 收集用户角色：
   - 直接角色：`sys_user_roles`。
   - 分组继承角色：`sys_groups` / `sys_group_roles`，递归父级。
2. 如果没有角色，尝试自动分配默认 `user` 角色。
3. 根据角色设置默认首页：
   - `admin` / `super` → `/analytics`
   - 其他 → `/user-home`
4. 调用 `jwt.Generate` 生成 Token 对：
   - AccessToken：包含 `user_id`、`username`、`roles`。
   - RefreshToken：包含 `user_id`。
5. 将 RefreshToken 做 SHA-256 哈希后保存到 Redis：

```text
refresh_token:{userID}
```

6. 使用 Lua 脚本保存，登录时新 Token 会覆盖旧 Token，并能记录是否覆盖了已有登录态。
7. 更新 `sys_users.last_login_at`、`sys_users.last_login_ip`。
8. Handler 写入 Cookie：

```text
access_token: HttpOnly, Secure, SameSite=Lax
refresh_token: HttpOnly, Secure, SameSite=Lax
```

## 4. 邮箱验证码登录流程

```text
前端获取图形验证码
  ↓
POST /auth/send-code 发送邮箱验证码（purpose=login）
  ↓
后端先校验图形验证码 captcha.Verify
  ↓
生成 6 位邮箱验证码，SHA-256 后写 Redis verify_code:login:{email}
  ↓
用户收到邮件验证码
  ↓
POST /auth/login-by-email
  ↓
VerifyCodeService.VerifyCode(email, code, "login")
  ↓
按 email 查询 sys_users
  ↓
复用 generateLoginResponse 生成登录态
```

关键点：

- 邮箱验证码发送前必须先过图形验证码，防止发送接口被刷。
- 邮箱验证码不明文存储，只保存 SHA-256 哈希。
- 验证成功后立即删除验证码 Redis Key。
- Handler 对大多数错误返回通用登录失败文案，避免泄露邮箱是否存在。

## 5. 手机号验证码登录流程

```text
前端获取图形验证码
  ↓
POST /auth/send-sms-code 发送短信验证码（purpose=login）
  ↓
后端先校验图形验证码 captcha.Verify
  ↓
生成 6 位短信验证码，SHA-256 后写 Redis sms_code:login:{phone}
  ↓
用户收到短信验证码
  ↓
POST /auth/login-by-phone
  ↓
VerifyCodeService.VerifySMSCode(phone, code, "login")
  ↓
按 phone 查询 sys_users
  ↓
复用 generateLoginResponse 生成登录态
```

关键点：

- 短信发送器由 `pkg/sms` 按配置选择阿里云或腾讯云。
- 发送失败时删除验证码和冷却标记，避免用户拿不到验证码却被占用验证码 Key。
- 同一手机号同一用途每天最多 10 次。

## 6. 注册流程中的验证码

```text
GET /auth/captcha
  ↓
POST /auth/send-code（purpose=register）
  ↓
图形验证码通过后发送邮箱验证码
  ↓
POST /auth/register
  ↓
VerifyCodeService.VerifyCode(email, emailCode, "register")
  ↓
事务内检查用户名和邮箱唯一性
  ↓
创建 sys_users
  ↓
分配默认 user 角色到 sys_user_roles
  ↓
记录 sys_security_logs
```

事务保护范围：

1. 用户名唯一性检查。
2. 邮箱唯一性检查。
3. 创建用户。
4. 分配默认角色。

这样可以降低并发注册造成重复用户或角色关系不完整的风险。

## 7. 重置密码流程中的验证码

```text
GET /auth/captcha
  ↓
POST /auth/send-code（purpose=reset_password）
  ↓
图形验证码通过后发送邮箱验证码
  ↓
POST /auth/reset-password
  ↓
VerifyCodeService.VerifyCode(email, emailCode, "reset_password")
  ↓
查询 sys_users
  ↓
检查 sys_password_history 最近 5 次密码
  ↓
更新 sys_users.password
  ↓
删除 refresh_token:{userID}
  ↓
删除 permission_codes:{userID}
  ↓
删除登录设备记录并记录安全日志
```

稳定性和安全点：

- 重置密码后删除 RefreshToken，旧会话不能继续刷新。
- 删除权限缓存，避免权限状态滞留。
- 删除登录设备，强制重新登录。
- 发送密码重置通知邮件，发送失败不阻断主流程。

## 8. 修改密码流程中的验证码

```text
认证用户携带 AccessToken
  ↓
GET /auth/captcha
  ↓
PUT /auth/change-password
  ↓
captcha.Verify 校验图形验证码
  ↓
校验旧密码 bcrypt
  ↓
保存旧密码到 sys_password_history
  ↓
更新 sys_users.password
  ↓
当前 AccessToken 写入 token_blacklist:{sha256(token)}
  ↓
删除 refresh_token:{userID}
  ↓
记录 sys_security_logs
```

修改密码接口不依赖登录失败触发阈值，而是固定要求图形验证码。

## 9. Token 刷新稳定流程

```text
POST /auth/refresh
  ↓
从 Cookie 读取 refresh_token
  ↓
jwt.Parse 校验签名、算法、过期时间
  ↓
查询用户和角色
  ↓
生成新的 AccessToken / RefreshToken
  ↓
Redis Lua 脚本原子校验旧哈希并替换新哈希
  ↓
写回 access_token / refresh_token Cookie
```

Redis Lua 脚本逻辑：

```text
stored = GET refresh_token:{userID}
if stored 不存在 → -1
if stored != sha256(oldRefreshToken) → 0
SETEX refresh_token:{userID} sha256(newRefreshToken) 30天
return 1
```

这个设计解决并发刷新稳定性问题：

- 两个刷新请求同时使用同一个 RefreshToken 时，只有第一个能替换成功。
- 第二个请求会因为 Redis 中已经是新哈希而失败。
- 避免旧 RefreshToken 被重复使用。

## 10. AccessToken 认证流程

认证中间件：`middleware.JWTAuth()`。

流程：

1. 从 `Authorization` 头读取 Bearer Token。
2. 调用 `jwt.Parse`：
   - 校验签名算法必须是 HS256。
   - 校验签名。
   - 校验过期时间。
3. 计算 Token SHA-256，检查 Redis 黑名单：

```text
token_blacklist:{sha256(accessToken)}
```

4. 检查设备是否被踢出：

```text
kicked_device:{userID}:{deviceID}
```

5. Redis 黑名单或踢出检查采用 fail-closed 策略：Redis 异常时拒绝请求，避免已失效 Token 被放行。
6. 将 `user_id`、`username`、`roles`、`device_id` 写入 Gin Context。

## 11. 风险评分验证码流程

认证后的接口还会经过 `CaptchaGuard`：

```text
JWTAuth 通过
  ↓
SecurityLogMiddleware
  ↓
CaptchaGuard
  ↓
判断是否属于受保护路径
  ↓
计算 IP 风险分
  ↓
风险分低：放行
  ↓
风险分高：要求 Header 中携带图形验证码
  ↓
验证码通过：写 captcha:whitelist:{ip}，风险分减半
```

高风险请求要求的请求头：

```text
X-Captcha-Id: <captchaId>
X-Captcha-Code: <captchaCode>
X-Captcha-Start-Time: <timestamp>
```

未提供或校验失败时返回：

```json
{
  "code": 403001,
  "data": {
    "captcha_type": "slider"
  },
  "error": null,
  "message": "当前操作需要验证码验证"
}
```

## 12. 使用到的数据表

| 表名 | 登录/验证码流程中的用途 |
|------|--------------------------|
| `sys_users` | 查询用户、密码哈希、状态、邮箱、手机号、最后登录时间/IP、强制改密标记 |
| `sys_roles` | 查询角色名称和权限码 |
| `sys_user_roles` | 查询或写入用户直接角色 |
| `sys_groups` | 用户分组层级 |
| `sys_group_roles` | 分组关联角色，支持递归继承 |
| `sys_system_settings` | 验证码配置、站点名、邮箱/短信/风控配置 |
| `sys_login_devices` | 登录成功后记录设备；踢出设备时配合 Redis 生效 |
| `sys_security_logs` | 记录登录、登录失败、注册、修改密码、重置密码等安全事件 |
| `sys_password_history` | 修改/重置密码时保存或检查历史密码 |

图形验证码、邮箱验证码、短信验证码没有单独 MySQL 表，使用 Redis 临时存储。

| `risk:window:{ip}` | `CaptchaGuard` | 滑动窗口访问记录 | 窗口时间 + 5 秒 |
| `captcha:whitelist:{ip}` | `CaptchaGuard` | 高风险验证码通过后的白名单 | 10 分钟 |

## 14. H5 支持改动范围评估

### 当前能否支持 H5

当前后端登录和验证码接口已经是标准 JSON API，H5 可以直接调用。并且当前已补齐推荐支持能力：注册来源、登录设备类型、RefreshToken Header/Body 刷新兼容。

当前已经可用的 H5 能力：

- 用户名密码登录。
- 图形验证码。
- 邮箱验证码发送和登录。
- 短信验证码发送和手机号登录。
- 注册。
- 重置密码。
- AccessToken 认证接口调用。

### 改动大不大

不大。后端核心认证链路不需要推倒重做，主要是补移动端识别和 Token 刷新兼容。

### 最小支持方案：不改代码

适用场景：H5 和后台同域，或 H5 是 HTTPS 浏览器页面，Cookie 能正常写入和携带。

需要做的事：

1. H5 使用现有接口。
2. 部署配置加入 H5 域名 CORS。
3. H5 请求开启 `withCredentials`。
4. H5 保存 `accessToken`，后续请求带 `Authorization`。
5. RefreshToken 继续依赖 `refresh_token` Cookie。

优点：无后端代码改动。

缺点：App WebView、跨域 H5、本地 HTTP 测试时 Cookie 可能不稳定。

### 已实现的推荐支持方案：小范围后端改动

适用场景：正式支持 H5 / App WebView / 小程序 WebView。

当前已完成以下改动：

#### 1. 注册来源支持 H5

`sys_users.register_source` 支持：

```text
web / h5 / miniapp / app
```

注册请求已支持：

```go
RegisterSource string `json:"registerSource"`
```

后端会做白名单归一化：

```text
web / h5 / miniapp / app
```

非法或为空默认 `web`，创建用户时写入 `RegisterSource`。

#### 2. 登录设备类型支持 H5

登录接口读取客户端 Header：

```http
X-Client-Type: h5
```

后端只允许白名单：

```text
web / h5 / miniapp / app
```

并写入 `sys_login_devices.device_type`。已有设备再次登录时，也会同步更新设备类型。

#### 3. RefreshToken 支持 Header / Body

`/auth/refresh` 支持三种来源：

```text
refresh_token Cookie
X-Refresh-Token Header
refreshToken 请求体字段
```

读取优先级：

```text
Cookie refresh_token → Header X-Refresh-Token → Body refreshToken
```

这样浏览器 H5、App WebView、非 Cookie 环境都能刷新 Token。

#### 4. CORS Header 补充

```yaml
  - Authorization
  - Content-Type
  - X-Device-ID
  - X-Client-Type
  - X-Refresh-Token
  - X-Captcha-Id
  - X-Captcha-Code
  - X-Captcha-Start-Time
  - X-CSRF-Token
```

## 15. 稳定性与安全总结

1. **图形验证码一次性消费**：Redis `GETDEL` 防止重放。
2. **图形验证码答案加密保存**：AES-GCM 加密 Redis 中的答案。
3. **邮箱/短信验证码哈希保存**：只保存 SHA-256，Redis 泄露也不直接暴露验证码。
4. **发送验证码有前置图形验证码**：防止邮箱/短信接口被批量滥用。
5. **发送冷却和每日次数限制**：降低验证码轰炸风险。
6. **失败计数与锁定**：验证码失败 5 次后短时间锁定。
7. **账号密码错误统一提示**：减少用户名枚举风险。
8. **RefreshToken 原子轮换**：Lua 脚本避免并发刷新竞态。
9. **AccessToken 黑名单**：登出和改密后可立即失效当前 Token。
10. **JWT 算法校验**：解析 Token 时强制 HS256，防止算法降级。
11. **JWT 中间件 fail-closed**：Redis 黑名单或设备踢出检查异常时拒绝请求。
12. **安全日志与设备记录**：登录、失败、注册、改密、重置均有审计记录。
