## 一、P2-17 — 班级邀请码双重体系清理（⚠️ 需要产品决策）

### 当前状况

班级系统存在 **两套邀请码**：

| 体系 | 字段/表 | 特性 | 生成方式 |
|---|---|---|---|
| **Class.code** | `classes.code`（6 位数字） | 固定不变，创建班级时自动生成 | 系统自动生成 |
| **ClassInvitation** | `class_invitations` 表 | 可设置使用次数、过期时间，可禁用 | 手动创建，支持多个 |

**问题表现**：
1. 班级详情页对 **所有成员** 都展示 `Class.code`，意味着任何人都能复制邀请码分享给外人
2. 两套邀请码功能重叠：都能让新用户加入班级
3. `Class.code` 无法控制使用次数和过期时间
4. 数据冗余，增加维护成本

### 需要产品决策

#### 方案 A：保留 ClassInvitation 动态体系（推荐）

- **删除** `Class.code` 作为邀请码的用途
- 创建班级时不生成 class code（或仅用于内部标识，不展示给成员）
- 班级详情页仅 teacher/monitor 可见邀请码管理入口
- 保留 `class_invitations` 表的多码、限时、限量特性
- **优点**：安全可控，可审计，符合企业场景
- **缺点**：需要迁移历史数据

#### 方案 B：保留 Class.code 单一固定码

- **移除** `class_invitations` 体系
- 只保留一个固定邀请码，不能设置过期和使用次数
- 简化用户操作
- **优点**：简单直观，无需额外管理
- **缺点**：无法控制邀请码泄露、无法撤销

#### 方案 C：两套并存但明确分工

- `Class.code` 作为永久班级识别码（用于 URL、API 等）
- `class_invitations` 作为临时加入凭证
- 前端明确区分展示
- **优点**：不做数据迁移
- **缺点**：系统复杂度高，用户容易混淆

### 建议

> 采用 **方案 A**。教育场景中邀请码泄露是真实风险，动态邀请码可设置过期/限量/禁用，更符合实际需求。

### 决策后实施工作量

| 步骤 | 工作量 |
|---|---|
| 数据库迁移（可选） | 30min |
| 后端修改 | 1h |
| 管理端前端修改 | 1h |
| 移动端前端修改 | 1h |
| 测试 + 部署 | 30min |
| **合计** | **~4h** |

## 三、P2-16 — 统一 createdAt / createTime 命名（⚠️ 高风险，需独立规划）

### 当前状况

前后端存在 **命名不一致**：

| 模块 | 当前使用 |
|---|---|
| GORM 模型（后端） | `CreatedAt` → JSON: `createTime` |
| 班级相关 | `CreatedAt` → JSON: `createdAt` |
| 管理端前端 | 混用 `createTime` / `createdAt` |
| 移动端前端 | 混用 `createTime` / `createdAt` |

### 统一方案建议

全项目统一使用 `createdAt`（GORM 约定 + ISO 8601 标准风格）。

### 涉及变更范围

| 层级 | 变更量 | 风险 |
|---|---|---|
| **后端 model** | `Question` 模型需改 `json:"createTime"` → `json:"createdAt"` | 🔴 高 — 所有 API 响应字段名变更 |
| **后端 service** | `toResponse()` 中 `CreatedAt` 格式 | 🟡 中 |
| **管理端前端** | API type 定义 + 表格列字段 | 🟡 中 — 需全面搜索替换 |
| **移动端前端** | API type 定义 + 页面字段 | 🟡 中 |
| **数据库** | 不需要改动（字段名 `created_at` 不变） | 🟢 低 |

### 风险点

1. 这是 **破坏性 API 变更**：所有消费 `createTime` 字端的客户端都需要同步更新
2. 如果移动端 App 已上架，旧版本用户会继续用 `createTime`，需要向后兼容
3. 管理端和移动端可能需要分别部署，存在版本不一致的窗口期

### 建议策略

1. **Phase 1**：后端同时支持 `createTime` 和 `createdAt`（双写双读，向后兼容）
2. **Phase 2**：前端全量迁移到 `createdAt`
3. **Phase 3**：后端移除 `createTime` 兼容

### 实施工作量

| 步骤 | 工作量 |
|---|---|
| 全项目搜索分析影响范围 | 1h |
| 后端兼容层开发 | 2h |
| 前端全面替换 | 3h |
| 回归测试 | 2h |
| **合计** | **~8h** |
