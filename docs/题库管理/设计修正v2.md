## 1. 高严重度问题修复

### 1.1 实施优先级矛盾修复

**问题**：主设计文档 13 节说"第一版全部落地 8 个二级菜单"，但 15 节分 P0-P3 四批，逻辑矛盾。

**修复**：统一为"首版范围" + "实现顺序"两个概念。

- **首版范围**：8 个二级菜单全部上线，功能完整可用。
- **实现顺序**：开发时按以下阶段推进，每个阶段可独立测试，不影响首版一次性交付：

| 阶段 | 覆盖菜单 | 说明 |
|---|---|---|
| Phase 1 | 题目管理（基础 CRUD + 发布） | 最小可用闭环：题目增删改查、富媒体题干/解析、发布生成版本 |
| Phase 2 | 题目导入、分类科目、知识考点 | 导入解析、分类树、知识点树、题目关联 |
| Phase 3 | 审核发布、题目分享、来源标签 | 审核队列、分组分享、来源管理、标签管理 |
| Phase 4 | 题库统计、题目管理（高级功能） | 统计面板、高级题型、组合题、查重、回收站 |

> 8 个菜单首版全部上线，但开发按 Phase 1→4 推进。每个阶段完成后功能独立可用，全部完成即为首版上线。

### 1.2 版本表快照字段补充

**问题**：`qb_question_versions` 未快照用户端展示/答题/判分必需的字段。

**修复**：版本表应增加以下快照字段：

```sql
ALTER TABLE qb_question_versions
  ADD COLUMN exam_id BIGINT UNSIGNED DEFAULT 0 COMMENT '快照：具体考试',
  ADD COLUMN subject_id BIGINT UNSIGNED DEFAULT 0 COMMENT '快照：科目/模块',
  ADD COLUMN category_id BIGINT UNSIGNED DEFAULT 0 COMMENT '快照：章节分类',
  ADD COLUMN source_id BIGINT UNSIGNED DEFAULT 0 COMMENT '快照：题目来源',
  ADD COLUMN difficulty TINYINT DEFAULT 1 COMMENT '快照：1简单 2中等 3困难',
  ADD COLUMN resource_type VARCHAR(20) DEFAULT 'private' COMMENT '快照：public/private/group/user',
  ADD COLUMN analysis_visible_policy VARCHAR(30) DEFAULT 'after_answer' COMMENT '快照：解析可见策略',
  ADD COLUMN answer_visible_policy VARCHAR(30) DEFAULT 'after_answer' COMMENT '快照：答案可见策略',
  ADD COLUMN parent_id BIGINT UNSIGNED DEFAULT 0 COMMENT '快照：父题ID（组合题）',
  ADD COLUMN is_group TINYINT DEFAULT 0 COMMENT '快照：是否组合题父题',
  ADD COLUMN sub_index INT DEFAULT 0 COMMENT '快照：子题排序';
```

> 核心规则：凡是用户端展示、答题、判分、筛选需要的字段，版本表都必须快照。编辑态修改这些字段不影响已发布版本。

### 1.3 越权防护规则

**问题**：无行级权限控制，有 `question:edit` 的用户可编辑他人题目。

**修复**：明确数据范围规则。

| 角色 | 数据范围规则 |
|---|---|
| 创作者 | `WHERE created_by = current_user_id AND resource_type = 'private'` |
| 内容管理员 | 可编辑公共题库中 `resource_type = 'public'` 的题目 |
| 教师/分组管理员 | 可编辑自己创建的和分享到自己管理分组的题目 |
| 超级管理员 | 无限制，可编辑所有题目 |

后端查询/修改时必须加入：

```go
// 伪代码：行级权限
func canEditQuestion(userID uint, question *Question) bool {
    if IsSuperAdmin(userID) { return true }
    if IsContentManager(userID) && question.ResourceType == "public" { return true }
    if question.CreatedBy == userID { return true }
    // 检查是否分享到用户管理的分组
    return IsGroupManagerOfQuestion(userID, question.ID)
}
```

审核操作额外校验：

```go
// 审核人不能审核自己的题目
func canApproveQuestion(operatorID uint, question *Question) bool {
    return question.CreatedBy != operatorID && HasPermission(operatorID, "question:audit:approve")
}
```

### 1.4 管理端/用户端权限隔离

**问题**：`question:view` 同时用于管理端和用户端。

**修复**：

| 端 | 接口前缀 | 权限码 | 数据范围 |
|---|---|---|---|
| 管理端 | `/api/v1/questions` | `question:view` | 按数据范围规则过滤 |
| 用户端 | `/api/v1/study/questions` | `study:view` 或 JWT 登录即可 | 只返回 `published` + 命中可见范围 |

用户端接口不需要 `question:view` 权限，只需登录态。可见范围由 `qb_question_visibility_scopes` 控制。

### 1.5 文件删除与题目附件冲突修复

**问题**：`sys_file_entries` 软删除后，题目版本快照中的附件引用失效。

**修复**：采用**引用计数 + 删除提示**方案。

1. `qb_question_attachments` 关联 `sys_file_entries.id` 时，增加引用计数（复用 `sys_file_assets.RefCount`）。
2. 文件删除前检查引用：
   - 如果文件被题库题目引用，**禁止直接删除**，提示"该文件被 N 道题目引用，请先解除关联"。
   - 或者采用**软标记**：文件软删除后，题目附件展示"文件已删除"占位，不影响题目结构。
3. 版本快照中的 `attachment_snapshot` 记录 fileId + fileName + contentType + size，即使文件被删除，快照仍保留元数据用于追溯。

### 1.6 组合题发布事务定义

**问题**：父子题版本可能部分成功，导致数据不一致。

**修复**：组合题发布必须作为数据库事务。

```text
BEGIN TRANSACTION
  1. 创建父题版本 → INSERT INTO qb_question_versions (parent题)
  2. 查询所有子题 → SELECT * FROM qb_questions WHERE parent_id = 父题ID
  3. 遍历子题创建版本 → INSERT INTO qb_question_versions (子题, parent_version_id=父题版本ID)
  4. 固化父题附件 → INSERT INTO qb_question_attachments (question_version_id=父题版本ID)
  5. 固化子题附件 → INSERT INTO qb_question_attachments (question_version_id=子题版本ID)
  6. 更新父题 current_version_id → UPDATE qb_questions SET current_version_id = 父题版本ID
  7. 更新子题 current_version_id → UPDATE qb_questions SET current_version_id = 子题版本ID
  8. 写入可见范围 → INSERT INTO qb_question_visibility_scopes (question_version_id=父题版本ID)
  9. 操作日志 → INSERT INTO qb_question_logs
如果任何一步失败 → ROLLBACK 全部
COMMIT
```

### 1.7 可见范围查询性能优化

**问题**：用户端查询可见题目需要 JOIN 多表，大数据量下性能差。

**修复**：

1. **public 范围**：直接查询 `qb_question_versions` WHERE `scope_type = 'public'`，不需要 JOIN。
2. **group/user/role 范围**：
   - 用户登录时，将可见范围写入 Redis 缓存：
     ```
     SET user:visible:groups:{userId} [group1, group2, ...]
     SET user:visible:roles:{userId} [role1, role2, ...]
     EXPIRE 3600
     ```
   - 查询时：
     ```sql
     -- 简化为 IN 查询，不需要多表 JOIN
     SELECT v.* FROM qb_question_versions v
     JOIN qb_question_visibility_scopes s ON v.id = s.question_version_id
     WHERE s.scope_type IN ('public', 'user')
        OR (s.scope_type = 'group' AND s.scope_id IN (:userGroups))
        OR (s.scope_type = 'role' AND s.scope_id IN (:userRoles))
     ```
3. **索引优化**：`qb_question_visibility_scopes` 的 `idx_qb_question_scope_lookup (scope_type, scope_id)` 已存在，足够支撑 IN 查询。
4. **缓存策略**：管理端发布/分享/下架时，清除相关用户的 Redis 可见范围缓存。

### 1.8 JSON 字段大小约束

**问题**：MySQL JSON 字段无内置大小限制，恶意数据可能撑大行大小。

**修复**：

1. 应用层校验（必须）：
   ```go
   const (
     MaxJSONSize      = 2 * 1024 * 1024  // 2MB 单字段
     MaxJSONDepth     = 10               // 最大嵌套深度
     MaxBlocksPerField = 50              // 单字段最大内容块数
   )
   ```
2. Go 校验函数：
   ```go
   func ValidateJSONField(data []byte) error {
     if len(data) > MaxJSONSize { return ErrJSONTooLarge }
     depth := CalculateJSONDepth(data)
     if depth > MaxJSONDepth { return ErrJSONTooDeep }
     return nil
   }
   ```
3. MySQL 层建议（可选）：
   ```sql
   -- MySQL 8.0+ CHECK 约束
   ALTER TABLE qb_questions
     ADD CONSTRAINT chk_stem_size CHECK (CHAR_LENGTH(JSON_UNQUOTE(JSON_COMPACT(stem))) < 2097152);
   ```

### 1.9 富媒体 HTML 净化方案

**问题**：未指定净化库和白名单规则。

**修复**：

1. 使用 Go 的 `bluemonday` 库自定义策略：
   ```go
   import "github.com/microcosm-cc/bluemonday"

   func SanitizeHTML(html string) string {
     p := bluemonday.UGCPolicy()
     // 允许的标签
     p.AllowElements("p", "br", "strong", "em", "u", "s", "blockquote", "code", "pre",
       "ul", "ol", "li", "h1", "h2", "h3", "h4", "h5", "h6", "table", "thead", "tbody",
       "tr", "th", "td", "a", "span", "div", "img", "sub", "sup", "hr")
     // 允许的属性
     p.AllowAttrs("href", "title").OnElements("a")
     p.AllowAttrs("src", "alt", "width", "height").OnElements("img")
     p.AllowAttrs("class").Globally()
     // src 只允许内部 fileId 引用（非 URL），外部 URL 的图片禁止
     p.RequireNoFollowOnLinks(true)
     p.RequireNoReferrerOnLinks(true)
     return p.Sanitize(html)
   }
   ```
2. 严格禁止：
   - `script`、`iframe`、`object`、`embed`、`form`、`link`、`meta`、`style`、`base`
   - 所有 `on*` 事件属性（`onerror`、`onclick`、`onload`、`onmouseover` 等）
   - `javascript:` 协议的 `href` / `src`
3. 图片 `src` 不使用外部 URL，只存储内部 fileId 引用：
   ```json
   { "type": "image", "fileId": 101 }
   ```
   前端渲染时通过 `/api/v1/files/:id/preview-url` 获取临时 URL。

### 1.10 分享码安全

**问题**：分享码可预测，存在暴力枚举风险。

**修复**：

1. 生成算法：使用 `crypto/rand` 生成 24 字节随机字符串，base64url 编码 = 32 字符。
   ```go
   func GenerateShareCode() (string, error) {
     b := make([]byte, 24)
     _, err := rand.Read(b)
     if err != nil { return "", err }
     return base64.RawURLEncoding.EncodeToString(b), nil
   }
   ```
2. 数据库唯一约束已存在：`UNIQUE KEY uk_qb_question_share_code (share_code)`。
3. 分享码长度 32 字符，62^32 种组合，无法暴力枚举。

### 1.12 after_exam_end 策略实现路径

**问题**：`after_exam_end` 策略依赖考试模块，但考试模块不在题库范围内。

**修复**：定义事件通知接口。

1. 考试模块到题库的事件通知：
   ```
   POST /api/v1/questions/events
   Body: { "event_type": "exam_ended", "exam_id": 123, "question_version_ids": [1,2,3] }
   ```
2. 题库收到 `exam_ended` 事件后，在 Redis 中记录：
   ```
   SET exam:ended:{examId} 1
   EXPIRE 86400
   ```
3. 用户端查询解析时：
   ```go
   if policy == "after_exam_end" {
     if !IsExamEnded(examId) {
       return ErrAnalysisNotAvailable
     }
   }
   ```
4. 第一版如果考试模块未就绪，`after_exam_end` 策略默认按 `never` 处理（用户端永不展示），直到考试模块接入。

### 1.13 收藏/错题与版本兼容性

**问题**：题目更新后，收藏/错题展示哪个版本不明确。

**修复**：

1. 收藏/错题记录同时保存 `question_id` 和 `question_version_id`：
   ```sql
   -- study_favorites（后续学习模块）
   question_id BIGINT UNSIGNED NOT NULL,
   question_version_id BIGINT UNSIGNED NOT NULL,
   ```
2. 展示规则：
   - 优先展示收藏时的版本（`question_version_id` 对应的版本）。
   - 如果该版本已 `deprecated` 或 `archived`，展示最新版本并提示"题目已更新，查看最新版本"。
   - 用户可选择查看历史版本或最新版本。
3. 错题本同理：错题快照保留答题时的题目版本内容，后续题目修改不影响历史错题记录。

### 1.14 题目编辑器分步保存

**问题**：一次性提交所有内容，网络异常或校验失败需重填。

**修复**：

1. **草稿自动保存**：
   - 前端每 30 秒或内容变化后 debounce 2 秒自动保存草稿。
   - 后端接口：`PUT /api/v1/questions/:id/draft` 只保存编辑态，不触发校验/发布。
2. **分步填写**（可选，第二版考虑）：
   - 第一步：基础信息 + 题干
   - 第二步：内容 + 答案
   - 第三步：解析 + 材料
   - 每步可独立保存，最后统一发布。
3. 草稿保存成功后，刷新页面可恢复未完成的编辑内容。

### 2.5 批量操作事务性和返回格式

批量接口统一返回格式：

```json
{
  "success": [1, 2, 3],
  "failed": [
    { "id": 4, "reason": "题目已被删除" },
    { "id": 5, "reason": "没有发布权限" }
  ]
}
```

实现规则：

1. 每道题独立处理，单题失败不影响其他题目。
2. 使用数据库事务包裹单题操作（非全量事务）。
3. 全部失败时返回 `success: []` 和完整 `failed` 列表。
4. 部分成功时 HTTP 状态码仍为 200，前端根据 `failed` 数量决定是否提示。

### 2.8 rejected 回到 pending 路径

状态流转更新：

```text
draft → pending → published
              └→ rejected → (修改后) → draft → 再次 submit-audit → pending
published → archived
archived → (管理员直接上架) → published
archived → (因审核驳回下架) → draft → 修改后 → submit-audit → pending
```

规则：

1. `rejected` 后题目自动回到 `draft` 状态。
2. 创建人修改后需手动再次"提交审核"。
3. `archived` 如果是管理员主动下架，可直接重新发布。
4. `archived` 如果因审核驳回导致，重新发布需再次走审核流程。

### 3.8 qb_question_logs action 分类

`qb_question_logs` 记录所有操作。分享和导入有独立表的同时，操作日志保留一条轻量记录用于审计追踪：

- `share` 日志只记录"创建了分享"，详细分享信息在 `qb_question_shares`。
- `import` 日志只记录"执行了导入"，详细导入信息在 `qb_question_import_tasks`。

两者职责不同：日志是审计 trail，业务表是详细数据。

### 3.10 source_id 与关系表关系

- `qb_questions.source_id` → 主来源（第一题只有一个主来源）。
- `qb_question_source_relations` → 一题多来源关系表（后续扩展）。
- `qb_question_sources.question_no` → 来源本身的原题号（该来源通用的题号）。

第一版只使用 `source_id`，`qb_question_source_relations` 表结构预留，后续启用。
