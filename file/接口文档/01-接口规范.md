# DevKit API 接口规范

> 作者：小胡
> 更新日期：2026/06/18

---

## 1. 基础信息

| 项目 | 说明 |
|------|------|
| Base URL | `/api/v1` |
| Content-Type | `application/json; charset=utf-8` |
| 字符编码 | UTF-8 |
| 协议 | HTTP/HTTPS |
| 数据格式 | JSON |

所有接口均以 `/api/v1` 作为路径前缀。例如登录接口完整路径为 `/api/v1/auth/login`。

---

## 2. 认证方式

### 2.1 Bearer Token（主要方式）

在请求头中携带 Access Token：

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

### 2.2 Cookie 备选

部分场景支持通过 Cookie 传递 Token，由后端在登录时自动设置：

```
Cookie: access_token=eyJhbGciOiJIUzI1NiIs...
```

### 2.3 Query 参数

对于图片/视频等资源标签（`<img>`、`<video>`），无法自定义请求头，支持通过 Query 参数传递 Token：

```
GET /api/v1/files/:id/view?token=eyJhbGciOiJIUzI1NiIs...
GET /api/v1/files/:id/stream?token=eyJhbGciOiJIUzI1NiIs...
```

### 2.4 临时预览 Token

文件预览等公开接口使用独立的临时 Token，有效期较短：

```
GET /api/v1/files/:id/preview?token=temp_xxxx
```

## 3. 请求格式

### 3.1 JSON 请求体

适用于大部分 POST/PUT 请求：

```
Content-Type: application/json

{
  "username": "admin",
  "password": "123456"
}
```

### 3.2 Query 参数

适用于 GET 请求的筛选、分页条件：

```
GET /api/v1/study/questions?page=1&pageSize=20&difficulty=1&categoryId=5
```

### 3.3 Path 参数

适用于资源定位：

```
GET /api/v1/study/questions/123
DELETE /api/v1/files/456
```

### 3.4 Form Multipart

适用于文件上传：

```
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

------WebKitFormBoundary
Content-Disposition: form-data; name="file"; filename="test.png"
Content-Type: image/png

(二进制数据)
------WebKitFormBoundary--
```

## 4. 响应格式

### 4.1 标准响应

所有接口统一返回以下 JSON 结构：

```json
{
  "code": 0,
  "data": {},
  "error": "",
  "message": ""
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | number | 状态码，`0` 表示成功，非 `0` 表示错误 |
| data | object/array | 响应数据，结构因接口而异 |
| error | string | 错误类型标识，成功时为空字符串 |
| message | string | 人类可读的消息，成功时通常为空 |

**成功示例：**

```json
{
  "code": 0,
  "data": {
    "id": 1,
    "username": "admin",
    "nickname": "管理员"
  },
  "error": "",
  "message": ""
}
```

**失败示例：**

```json
{
  "code": 400,
  "data": null,
  "error": "INVALID_PARAMS",
  "message": "用户名不能为空"
}
```

### 4.2 分页响应

分页接口返回带分页信息的结构：

```json
{
  "code": 0,
  "data": {
    "items": [
      {"id": 1, "name": "题目1"},
      {"id": 2, "name": "题目2"}
    ],
    "total": 100
  },
  "error": "",
  "message": ""
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| items | array | 当前页数据列表 |
| total | number | 总记录数 |

**分页请求参数：**

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| page | number | 否 | 1 | 页码，从 1 开始 |
| pageSize | number | 否 | 20 | 每页条数，最大 100 |

## 5. 错误码

| 错误码 | HTTP 状态码 | 说明 |
|--------|-------------|------|
| `0` | 200 | 成功 |
| `400` | 400 | 请求参数错误 |
| `401` | 401 | 未授权（未登录或 Token 过期） |
| `403` | 403 | 禁止访问（无权限） |
| `404` | 404 | 资源未找到 |
| `500` | 500 | 服务器内部错误 |
| `429` | 429 | 请求过于频繁（限流） |
| `400001` | 400 | 配额超限（如存储空间不足） |
| `403001` | 403 | 需要验证码（未完成人机验证） |

### 5.1 错误响应示例

**参数校验失败（400）：**

```json
{
  "code": 400,
  "data": null,
  "error": "VALIDATION_ERROR",
  "message": "用户名长度不能少于3个字符"
}
```

**未授权（401）：**

```json
{
  "code": 401,
  "data": null,
  "error": "UNAUTHORIZED",
  "message": "Token已过期，请重新登录"
}
```

**无权限（403）：**

```json
{
  "code": 403,
  "data": null,
  "error": "FORBIDDEN",
  "message": "没有权限执行此操作"
}
```

**限流（429）：**

```json
{
  "code": 429,
  "data": null,
  "error": "RATE_LIMIT_EXCEEDED",
  "message": "请求过于频繁，请稍后再试"
}
```

**需要验证码（403001）：**

```json
{
  "code": 403001,
  "data": null,
  "error": "CAPTCHA_REQUIRED",
  "message": "请先完成人机验证"
}
```

## 6. 限流说明

系统采用两层限流机制：

### 6.1 IP 令牌桶限流

基于客户端 IP 地址的令牌桶算法，保护服务器免受突发流量冲击。

- 默认每个 IP 每秒允许一定数量的请求
- 超出限制返回 `429 Too Many Requests`

### 6.2 数据库规则限流

支持管理员自定义限流规则，基于数据库配置：

| 配置项 | 说明 |
|--------|------|
| 路径匹配 | 支持精确路径和通配符 |
| 时间窗口 | 秒/分/时/天 |
| 最大请求数 | 时间窗口内允许的最大请求数 |
| 限流维度 | IP / 用户 / 接口 |

限流规则通过 `/api/v1/system/rate-limit-rules` 接口管理。

## 7. CSRF 保护

系统采用 **Double Submit Cookie** 模式防止 CSRF 攻击：

1. 服务端在 Cookie 中设置 `csrf_token`
2. 客户端从 Cookie 中读取该值，在后续请求中通过 `X-CSRF-Token` 请求头回传
3. 服务端比对 Cookie 和 Header 中的 Token 是否一致

```
Cookie: csrf_token=abc123
Header: X-CSRF-Token: abc123
```

**注意：** CSRF Token 仅用于状态变更请求（POST/PUT/DELETE），GET 请求无需携带。

## 8. 自定义请求头

系统支持以下自定义请求头，用于客户端标识和功能控制：

| 请求头 | 说明 | 是否必填 |
|--------|------|----------|
| `X-Device-ID` | 设备唯一标识，用于多设备管理 | 建议携带 |
| `X-Client-Type` | 客户端类型（web/ios/android/miniapp） | 建议携带 |
| `X-Mobile-Token-Mode` | 移动端 Token 模式（short/long） | 移动端必填 |
| `X-App-Version` | 应用版本号 | 建议携带 |
| `X-System-Version` | 系统版本（如 iOS 17.0） | 建议携带 |
| `X-Device-Model` | 设备型号（如 iPhone 15 Pro） | 建议携带 |
| `X-Platform` | 平台标识 | 建议携带 |
| `X-Channel` | 渠道标识 | 建议携带 |
| `X-Refresh-Token` | 刷新 Token（用于 Token 刷新接口） | 按需 |
| `X-CSRF-Token` | CSRF Token | 状态变更请求 |
| `X-Request-ID` | 请求追踪 ID | 建议携带 |
